# Rust GPU GUI 라이브러리 설계 조사

## 질문

Solid.js 2.0 스타일의 단일 스레드 반응형 런타임 `signals`가 이미 있습니다. 런타임은 `Owner`로 계산과 구독의 수명을 관리합니다. `wake_host`가 호스트를 깨우면 호스트는 `flush`로 `Frame<P>`를 받습니다. `FrameOp<P>`의 `Attach`, `SetVisible`, `Patch`, `Remove`를 GUI에 연결하려면 어떤 서브시스템이 필요하며, 어떤 크레이트와 설계부터 검증하면 됩니까?

기준일은 2026년 11월 24일입니다. 조사 노트 다섯 편을 종합했습니다. 문서나 소스가 직접 확인해 주는 사실에는 [Direct], 서로 독립적인 구현에서 확인한 공통점에는 [Supported], 이 프로젝트에 적용할 설계 판단에는 [Inferred]를 붙였습니다.

## 핵심 답변

[Inferred] 첫 데스크톱 구현은 **winit 0.30.13, wgpu 30.0.2, Taffy 0.16.0, COSMIC Text 0.19.0과 Swash, AccessKit 0.25.2와 accesskit_winit 0.34.2** 조합을 후보로 삼습니다. 창마다 노드 ID와 자식 순서를 유지하는 UI 트리를 두고, UI 스레드가 `flush`로 받은 프레임을 적용합니다. 계층별 변경 여부에 따라 레이아웃, 입력에 쓰는 좌표와 클립, 그리기 명령, 접근성 트리를 갱신합니다. 이 조합의 빌드와 구동은 조사 범위에서 확인하지 못했습니다. [Winit 릴리스 기록](https://docs.rs/crate/winit/latest) (0.30.13 (2026-03-02), 0.31.0-beta.4 (2026-10-24)), [wgpu 릴리스 기록](https://github.com/gfx-rs/wgpu/releases) (30.0.2 (2026-11-12)), [Taffy 레이아웃 API](https://docs.rs/taffy/latest/taffy/) (0.16.0 (2026-11-23)), [COSMIC Text API](https://docs.rs/cosmic-text/0.19.0/cosmic_text/) (0.19.0 (2026-04-22)), [AccessKit winit 패키지와 의존성](https://docs.rs/crate/accesskit_winit/latest) (0.34.2 (2026-10-25))

버튼, 텍스트, 스크롤을 먼저 지원한다면 wgpu에서 사각형과 글리프를 배치로 그리는 방식으로 시작할 수 있습니다. 복잡한 벡터 경로와 그룹 합성이 첫 제품 범위에 들어가면 같은 장면을 Vello 계열이나 Skia에서도 시험해 렌더러를 정합니다. 첫 검증 단위는 **키가 있는 목록, 포커스를 받을 수 있는 버튼과 한 줄 입력 필드를 넣은 창**입니다. 실제 창에서 키보드 탐색, 한글 IME 조합, 화면 읽기 프로그램의 조작까지 확인하면 시그널 런타임이 맡는 일과 GUI가 추가로 맡아야 할 일이 드러납니다. [GPUI wgpu 렌더러 소스](https://github.com/zed-industries/zed/blob/main/crates/gpui_wgpu/src/wgpu_renderer.rs) (main, 날짜 미기재), [Vello 렌더러 아키텍처](https://github.com/linebender/vello/blob/main/ARCHITECTURE.md) (main, 날짜 미기재), [Rust-Skia API](https://docs.rs/skia-safe/latest/skia_safe/) (0.157.0 (2026-11-03)), [AccessKit winit Adapter](https://docs.rs/accesskit_winit/latest/accesskit_winit/struct.Adapter.html) (0.34.2)

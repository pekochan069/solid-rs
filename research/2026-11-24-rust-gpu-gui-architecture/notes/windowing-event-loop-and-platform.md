## 1. What do the Rust windowing options offer for multi-window GPU GUIs?

### Takeaway

Winit 0.30 exposes one main-thread event loop, window IDs, and native handles for a renderer chosen by the application. Tao and SDL3 also support that division of work, with different event-loop and native-library dependencies. GPUI’s platform code gives a reference for a backend that also owns text, rendering, and native services.

### Cited findings

- The registry lists **winit 0.30.13** as stable, dated 2026-03-02, and **0.31.0-beta.4** as a prerelease, dated 2026-10-24. Stable winit’s own multi-window example creates windows through `ActiveEventLoop`, stores them by `WindowId`, and routes each `WindowEvent` by ID. The builder docs say the event loop “must be created on the main thread, and only once per application” for portability. [Winit registry](https://docs.rs/crate/winit/latest), [multi-window example](https://github.com/rust-windowing/winit/blob/v0.30.13/examples/window.rs), [event-loop builder](https://docs.rs/winit/0.30.13/winit/event_loop/struct.EventLoopBuilder.html), 0.30.13 and 0.31.0-beta.4, accessed 2026-07-01, Direct.
- The 0.31 development docs expose `&dyn ActiveEventLoop` and `ApplicationHandler::proxy_wake_up`. Stable 0.30 uses `ApplicationHandler<T>::user_event` with typed events. The beta release line also adds native popup positioning and clipboard APIs, so the choice of API generation affects windowing and service integration. [Stable `ApplicationHandler`](https://docs.rs/winit/latest/winit/application/trait.ApplicationHandler.html), [development `ApplicationHandler`](https://rust-windowing.github.io/winit/winit/application/trait.ApplicationHandler.html), [0.31 release notes](https://github.com/rust-windowing/winit/releases), 0.30.13, 0.31 development docs, and 0.31.0-beta.3–4, accessed 2026-07-01, Direct.
- **raw-window-handle 0.6.2**, dated 2024-05-17, standardizes native window and display handles for graphics interoperability. In the maintainers’ words, it “does not provide any utilities for creating and managing windows.” Winit and Tao list optional 0.6 support. The SDL3 binding lists optional 0.6.2 support. [Raw window handle docs](https://docs.rs/raw-window-handle/0.6.2/raw_window_handle/), [registry history](https://docs.rs/crate/raw-window-handle/latest), [winit dependencies](https://docs.rs/crate/winit/latest), [Tao dependencies](https://docs.rs/crate/tao/latest), [SDL3 binding dependencies](https://docs.rs/crate/sdl3/latest), relevant versions 0.6.2, 0.30.13, 0.37.3, and 0.22.1, accessed 2026-07-01, Direct.
- **Tao 0.37.3**, dated 2026-11-18, is maintained by Tauri. It uses the closure-based `EventLoop::run` API, an `EventLoopProxy` for custom events, and window/display handles for attaching a renderer. Its Linux build depends on GTK 3. The maintainer lists Windows, macOS, Linux, iOS, and Android. [Tao registry](https://docs.rs/crate/tao/latest), [Tao crate docs](https://docs.rs/tao/0.37.3/tao/), [Tao maintainer README](https://github.com/tauri-apps/tao/blob/dev/README.md), 0.37.3 and development README, accessed 2026-07-01, Direct.
- **sdl3 0.22.1**, dated 2026-11-09, binds the native SDL3 library and offers optional raw-handle integration. SDL assigns window IDs to native events, so an event loop can route them to several windows. SDL’s native runtime also supplies input, clipboard, and dialog APIs. Its event-pump model is different from `ApplicationHandler`. [SDL3 Rust registry](https://docs.rs/crate/sdl3/latest), [SDL window IDs](https://wiki.libsdl.org/SDL3/SDL_GetWindowID), [SDL event wait](https://wiki.libsdl.org/SDL3/SDL_WaitEvent), [SDL file dialog](https://wiki.libsdl.org/SDL3/SDL_ShowFileDialogWithProperties), Rust binding 0.22.1 and SDL 3.2+ APIs, accessed 2026-07-01, Direct.
- The `gpui` registry lists **0.2.2**, dated 2025-10-22. Zed’s current source has a separate `gpui_platform` convenience crate that instantiates platform-specific implementations and hands them to `gpui::Application`. The README documents Win32 and DirectWrite on Windows, Metal on macOS, and Wayland and X11 choices on Linux and FreeBSD. Linux windowing features also compile the renderer and text system. Those source-tree APIs have a different provenance from the published 0.2.2 package. [GPUI registry](https://docs.rs/crate/gpui/latest), [platform constructor](https://github.com/zed-industries/zed/blob/main/crates/gpui_platform/src/gpui_platform.rs), [GPUI README](https://github.com/zed-industries/zed/blob/main/crates/gpui/README.md), 0.2.2 and undated `main` source, accessed 2026-07-01, Direct.

### Inferences

- A host built around winit or Tao could keep the reactive runtime, per-window state, and GPU renderer under its own ownership. Extracting GPUI’s native backends for the same job would likely require adapting GPUI’s application, renderer, and text-system contracts. [Winit multi-window example](https://github.com/rust-windowing/winit/blob/v0.30.13/examples/window.rs), [Tao crate docs](https://docs.rs/tao/0.37.3/tao/), [GPUI platform constructor](https://github.com/zed-industries/zed/blob/main/crates/gpui_platform/src/gpui_platform.rs), Inferred.
- The backend choice depends in part on who owns the process event loop. Winit has an external pumping API with platform and synchronous-delivery caveats. SDL’s polling and waiting calls give the host a different integration point, with native live-resize behavior of their own. [Winit external event pumping](https://docs.rs/winit/0.30.13/winit/platform/pump_events/trait.EventLoopExtPumpEvents.html), [SDL on live resize](https://wiki.libsdl.org/SDL3/AppFreezeDuringDrag), Inferred.

### Gaps

- The release and source searches did not establish a standalone, independently versioned GPUI platform API for a host that replaces GPUI’s renderer and UI runtime.
- The crate docs establish API availability. The searches did not yield a primary test matrix comparing multiple windows across mixed-DPI or mixed-refresh monitors for all four options.

## 2. How do GUI frameworks bridge a thread-safe wake and pace frames?

### Takeaway

A wake makes pending application work visible to the UI thread. A redraw gives a particular window an opportunity to display that work, and GPU presentation determines when the rendered image reaches the display. Winit exposes a separate mechanism for each.

### Cited findings

- In stable winit, `EventLoopProxy<T>` is `Send` and `Sync` when `T` is `Send`. `send_event` routes a payload to `ApplicationHandler::user_event`. `Wait` sleeps until an event arrives, and `WaitUntil` adds a deadline. `Poll` starts another iteration immediately. Winit’s `ControlFlow` docs point continuous native-refresh rendering toward `Poll` with graphics-API vsync. [Event-loop proxy](https://docs.rs/winit/0.30.13/winit/event_loop/struct.EventLoopProxy.html), [application handler](https://docs.rs/winit/latest/winit/application/trait.ApplicationHandler.html#method.user_event), [control flow](https://docs.rs/winit/0.30.13/winit/event_loop/enum.ControlFlow.html), 0.30.13, accessed 2026-07-01, Direct.
- Winit’s stable source says it “will aggregate duplicate redraw requests into a single event.” `request_redraw` also integrates with OS invalidation. The handler docs direct rendering to `RedrawRequested` and say high-frequency input can generate many `AboutToWait` events. `request_redraw` carries no guarantee about delivery in the current or next iteration. [Winit event source](https://github.com/rust-windowing/winit/blob/v0.30.13/src/event.rs), [application handler](https://docs.rs/winit/latest/winit/application/trait.ApplicationHandler.html#method.about_to_wait), [`Window::request_redraw`](https://docs.rs/winit/0.30.13/winit/window/struct.Window.html#method.request_redraw), 0.30.13, accessed 2026-07-01, Direct.
- `Window::pre_present_notify()` goes after drawing and before handing the buffer to the window system. On Wayland it registers a compositor frame callback to throttle subsequent redraw events. Winit documents Windows redraw delivery in sync with `WM_PAINT`. Wgpu’s FIFO presentation mode drains the queue at vertical blank and documents that texture acquisition can block while the queue is full. [Winit presentation notification](https://docs.rs/winit/0.30.13/winit/window/struct.Window.html#method.pre_present_notify), [winit redraw behavior](https://docs.rs/winit/0.30.13/winit/window/struct.Window.html#method.request_redraw), [wgpu FIFO](https://docs.rs/wgpu/latest/wgpu/enum.PresentMode.html#variant.Fifo), 0.30.13 and wgpu 30.0.2, accessed 2026-07-01, Direct.
- Iced’s runner creates a proxy from `event_loop.create_proxy()` and passes it into its async runtime. It requests redraws for due windows, tracks the next redraw deadline with `WaitUntil`, and uses `Wait` when it has no scheduled deadline. It invokes `pre_present_notify` through a compositor callback. [Iced winit runner](https://github.com/iced-rs/iced/blob/master/winit/src/lib.rs), undated `master` source, accessed 2026-07-01, Direct.
- Masonry collects redraw requests by window ID and issues one `request_redraw` per affected window after processing signals. It routes `RedrawRequested` to that window’s renderer, reconciles the surface size during redraw, and calls `pre_present_notify` before presentation. [Masonry winit event-loop runner](https://github.com/linebender/xilem/blob/main/masonry_winit/src/event_loop_runner.rs), undated `main` source, accessed 2026-07-01, Direct.
- GPUI’s current macOS code starts a Metal frame source or a window display-link source and checks whether AppKit reports the window visible before starting it. SDL documents a different native issue. An event-pump call may block during interactive resize or move, particularly on Windows. SDL documents main callbacks or an event watch on `SDL_EVENT_WINDOW_EXPOSED` for redraw opportunities during that operation. SDL also documents that generic event watchers may run on a different thread, and `SDL_PushEvent` is callable from any thread. [GPUI macOS window implementation](https://github.com/zed-industries/zed/blob/main/crates/gpui_macos/src/window.rs), [SDL live-resize note](https://wiki.libsdl.org/SDL3/AppFreezeDuringDrag), [event-watch threading](https://wiki.libsdl.org/SDL3/SDL_AddEventWatch), [event push](https://wiki.libsdl.org/SDL3/SDL_PushEvent), undated Zed `main` source and SDL 3.2+ APIs, accessed 2026-07-01, Direct.

### Inferences

- A `Send + Sync` callback could publish a wake token through the proxy, with the UI thread retaining ownership of the reactive runtime. If the host coalesces wakes, it needs to re-arm the wake before draining pending work or explicitly recheck the queue afterward, so an update racing the drain still reaches the UI thread. Per-window dirty state would let one runtime flush invalidate several windows whose redraws arrive separately. [Winit proxy](https://docs.rs/winit/0.30.13/winit/event_loop/struct.EventLoopProxy.html), [Masonry signal handling](https://github.com/linebender/xilem/blob/main/masonry_winit/src/event_loop_runner.rs), Inferred.
- For an idle or mostly static GUI, `Wait` with explicit redraws appears to fit the sourced framework patterns. An animation may need a deadline, a compositor frame callback, or continuous presentation. A missed deadline and a missed state update are distinct failures. Coalescing can preserve the latest state even when intermediate visual states never reach the display. [Winit control flow](https://docs.rs/winit/0.30.13/winit/event_loop/enum.ControlFlow.html), [Iced runner](https://github.com/iced-rs/iced/blob/master/winit/src/lib.rs), [wgpu FIFO](https://docs.rs/wgpu/latest/wgpu/enum.PresentMode.html#variant.Fifo), Inferred.
- A resize handler could record the latest physical extent and request a frame. The redraw path could reconfigure the GPU surface once for that extent and skip surface acquisition while either dimension is zero. Handling the OS redraw in its callback gives native resize loops a chance to display the current content. [Masonry runner](https://github.com/linebender/xilem/blob/main/masonry_winit/src/event_loop_runner.rs), [wgpu surface configuration](https://docs.rs/wgpu/latest/wgpu/type.SurfaceConfiguration.html), [SDL live-resize note](https://wiki.libsdl.org/SDL3/AppFreezeDuringDrag), Inferred.

### Gaps

- The framework and API searches did not yield a portable guarantee of one frame per vertical blank. They also did not yield measurements for latency or missed frames during interactive resize or when multiple windows present on different displays.
- GPUI’s macOS source establishes one display-linked implementation. I did not verify an equivalent Windows or Linux implementation with a fixed source revision.

## 3. Which desktop platform services need additional integration?

### Takeaway

Winit 0.30 supplies scale, composition, and file-drop event types. Coverage varies by backend. Clipboard, native menus, native dialogs, and Linux theme monitoring have dedicated integrations with their own platform requirements.

### Cited findings

- **DPI and resize.** Winit’s `inner_size()` reports physical client-area pixels. `ScaleFactorChanged` reports the new scale and provides an inner-size writer for applications that need to override the OS suggestion. The window docs advise tracking scale changes when a window moves across displays. Wayland also restricts querying and setting desktop window positions. [Winit window API](https://docs.rs/winit/0.30.13/winit/window/struct.Window.html), [winit event source](https://github.com/rust-windowing/winit/blob/v0.30.13/src/event.rs), 0.30.13, accessed 2026-07-01, Direct.
- **IME.** Winit exposes `set_ime_allowed`, `set_ime_cursor_area`, and `Ime::{Enabled, Preedit, Commit, Disabled}`. The preedit selection uses byte offsets. The cursor-area API lets the OS place its candidate box near the edited text. Winit 0.30 sends an empty preedit before commit, and the 0.31 beta.4 release changes that sequence. SDL has `SDL_StartTextInput` and `SDL_SetTextInputArea` for the same class of integration. [Winit window IME methods](https://docs.rs/winit/0.30.13/winit/window/struct.Window.html#method.set_ime_allowed), [winit IME events](https://github.com/rust-windowing/winit/blob/v0.30.13/src/event.rs), [beta.4 release notes](https://github.com/rust-windowing/winit/releases/tag/v0.31.0-beta.4), [SDL text input](https://wiki.libsdl.org/SDL3/SDL_StartTextInput), [SDL input area](https://wiki.libsdl.org/SDL3/SDL_SetTextInputArea), 0.30.13, 0.31.0-beta.4, and SDL 3.2+, accessed 2026-07-01, Direct.
- **Clipboard.** **arboard 3.7.0**, dated 2026-10-15, documents text and image operations on Windows, macOS, and Linux. Its Linux default uses X11 or XWayland. `wayland-data-control` enables the native path where the compositor supports its protocol. On Linux, dropping the final `Clipboard` instance can make its owned contents unavailable. Winit 0.31 beta.4 adds its own clipboard APIs for Wayland, X11, macOS, and Windows, plus primary selection on Wayland and X11. [Arboard registry](https://docs.rs/crate/arboard/latest), [arboard backend README](https://github.com/1Password/arboard/blob/v3.7.0/README.md), [clipboard lifetime docs](https://docs.rs/arboard/3.7.0/arboard/struct.Clipboard.html), [winit beta.4 release](https://github.com/rust-windowing/winit/releases/tag/v0.31.0-beta.4), 3.7.0 and 0.31.0-beta.4, accessed 2026-07-01, Direct.
- **Drag-and-drop.** Winit 0.30 has path-based `HoveredFile`, `DroppedFile`, and `HoveredFileCancelled` events. SDL’s `SDL_DropEvent` carries a window ID and supports inbound text and file drops. The existence of an event type establishes the payload a backend can supply. [Winit event source](https://github.com/rust-windowing/winit/blob/v0.30.13/src/event.rs), [SDL drop event](https://wiki.libsdl.org/SDL3/SDL_DropEvent), 0.30.13 and SDL 3.2+, accessed 2026-07-01, Direct.
- **Native menus.** **muda 0.21.2**, dated 2026-10-08, uses Win32, AppKit, and GTK 3 or 4 on Linux and BSD. Its README says Windows accelerators require the message loop to call `TranslateAcceleratorW`. Winit supplies a Windows `with_msg_hook` for integrating native message processing. On Linux, muda’s GTK dependency makes a native menu an integration task in a winit app. [Muda registry](https://docs.rs/crate/muda/latest), [muda platform notes](https://github.com/tauri-apps/muda/blob/muda-v0.21.2/README.md), [winit Windows message-hook docs](https://docs.rs/winit/latest/winit/platform/windows/trait.EventLoopBuilderExtWindows.html#tymethod.with_msg_hook), 0.21.2 and winit 0.30.13, accessed 2026-07-01, Direct.
- **Native dialogs.** **rfd 0.18.0**, dated 2026-11-07, exposes synchronous and asynchronous file dialogs and supports setting a parent using window and display handles. On Linux and BSD its default backend is the XDG Desktop Portal. GTK 3 and GTK 4 are selectable backends, and the portal path depends on the installed desktop services. [Rfd registry](https://docs.rs/crate/rfd/latest), [platform and backend docs](https://docs.rs/rfd/0.18.0/rfd/), [async file-dialog API](https://docs.rs/rfd/latest/rfd/struct.AsyncFileDialog.html), 0.18.0, accessed 2026-07-01, Direct.
- **System theme.** Winit 0.30 marks `ThemeChanged` unsupported on X11 and Wayland. Its Wayland `Window::theme()` reports overrides only. **dark-light 3.0.0**, dated 2026-08-12, documents detection and change subscriptions. **ashpd 0.14.3** exposes `Settings::color_scheme()` and `receive_color_scheme_changed()` for the XDG portal. [Winit event source](https://github.com/rust-windowing/winit/blob/v0.30.13/src/event.rs), [winit theme query](https://docs.rs/winit/0.30.13/winit/window/struct.Window.html#method.theme), [dark-light registry](https://docs.rs/crate/dark-light/latest), [dark-light APIs](https://docs.rs/dark-light/3.0.0/dark_light/), [ashpd settings API](https://docs.rs/ashpd/latest/ashpd/desktop/settings/struct.Settings.html), 0.30.13, 3.0.0, and 0.14.3, accessed 2026-07-01, Direct.
- **Accessibility hook points.** **accesskit_winit 0.34.2**, dated 2026-10-25, documents creating a per-window adapter before the window becomes visible and calling `process_event` before the application handles each window event. Its proxy constructor can deliver adapter events through the same typed main-loop channel as other host events. [AccessKit winit registry](https://docs.rs/crate/accesskit_winit/latest), [adapter setup and event routing](https://docs.rs/accesskit_winit/latest/accesskit_winit/struct.Adapter.html), 0.34.2, accessed 2026-07-01, Direct.

### Inferences

- Scale belongs to each window. Keeping layout in logical units and GPU extents in physical pixels would give a consistent basis for hit testing, candidate-window placement, and rendering when a window crosses displays. IME composition also needs its own edit state so a temporary preedit can be replaced or cleared before committing text. [Winit window API](https://docs.rs/winit/0.30.13/winit/window/struct.Window.html), [winit event source](https://github.com/rust-windowing/winit/blob/v0.30.13/src/event.rs), Inferred.
- A native menu command, theme change, or completed async dialog can plausibly enter the same UI-thread dispatch path as a runtime wake while retaining its own event type. This leaves the backend-specific menu and parent-window requirements at the platform integration point. [Winit proxy](https://docs.rs/winit/0.30.13/winit/event_loop/struct.EventLoopProxy.html), [muda platform notes](https://github.com/tauri-apps/muda/blob/muda-v0.21.2/README.md), [rfd async dialog API](https://docs.rs/rfd/latest/rfd/struct.AsyncFileDialog.html), Inferred.

### Gaps

- The drag-and-drop search returned downstream reports that native Wayland file drops were absent in winit 0.30 and added in 0.31 beta.3. The primary implementation PR timed out. The evidence here does not establish the exact release and backend matrix for incoming files, arbitrary MIME payloads, or outgoing drags.
- API docs do not establish behavior across Linux compositors and portal implementations for clipboard persistence, dark-mode notifications, dialogs, or IME. The searches did not yield a first-party cross-platform parity matrix for those services.

- Compare renderer-level surface recovery under minimize, interactive resize, and monitor transfers. Masonry’s per-window redraw and surface handling provides a concrete source path. [Masonry winit event-loop runner](https://github.com/linebender/xilem/blob/main/masonry_winit/src/event_loop_runner.rs).
- Check the text editor’s composition and surrounding-text model against native IMEs. The beta release history records changes in preedit clearing and additional IME APIs that affect event translation. [Winit release history](https://github.com/rust-windowing/winit/releases).
- Verify the window-open sequence with an accessibility adapter and a native menu or dialog attached. The API docs establish the setup requirements individually. [AccessKit winit adapter](https://docs.rs/accesskit_winit/latest/accesskit_winit/struct.Adapter.html), [muda platform notes](https://github.com/tauri-apps/muda/blob/muda-v0.21.2/README.md), [rfd async file dialogs](https://docs.rs/rfd/latest/rfd/struct.AsyncFileDialog.html).

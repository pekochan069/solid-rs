## Key Question 1: Documented problems in Solid 1.x that motivated Solid 2.0's async reactivity design

### Takeaway

Solid 2.0's official RFCs and migration docs document that `createResource` and explicit `startTransition`/`useTransition` created parallel reactive and error-handling models, leaked `T | undefined` loading holes into types, lacked granular/race-safe optimistic updates, and forced developers to manually wire scheduling concerns (`batch`, `startTransition`) that the graph now handles automatically.

### Cited findings

- **Parallel models and `T | undefined` type leaks:** Solid 2.0's async RFC states its motivation directly:
  > "**One model:** Async shouldn’t require a parallel set of primitives (resources vs signals). If computations can be async, the rest of the system (effects, boundaries, SSR/hydration) can treat async consistently. **Better types:** Async values can be represented without pervasive `T | undefined` “loading holes”. UI should be expressed via `Loading` boundaries rather than nullable types. **Composability:** When async is part of computations, derived values can combine sync + async naturally without bespoke resource combinators."
  [RFC: Async data (05-async-data.md)](file:///C:/Users/thinl/dev/solid/documentation/solid-2.0/05-async-data.md#L13-L15), `solid-js@2.0.3 (commit fcaa0510)`, RFC frozen `2.0.0 (2026-11-17)`, accessed 2026-11-23, Direct.
- **Function coloring / "colorless" async:** Secondary summaries of Ryan Carniato's Solid 2.0 design work report that Solid 2.0 aims for "colorless" async reactivity so computations returning Promises or async iterators compose with downstream readers without async/sync function coloring spreading through consumers. [dev.to via search summary](https://vertexaisearch.cloud.google.com/grounding-api-redirect/AUZIYQGLJPdjEg8cDGbRLNMrpbfNlupEKo_cw1I2tn9V30CR6bIVt-f9ua7d05f9SEKWrgIU99Ary8kbyIIoQiP-8HqMqpZNhQ_TJCgojmkI1DbZTQxyHsxIfXW8-8VGr82Z2woUN6GKNUAkc0vcI6Yv7NeBj0qvGVbwvuH-QQ==), undated, accessed 2026-11-23, Supported (secondary summary).
- **Split error paths (`resource.error` vs `ErrorBoundary`):** In 1.x, `resource.error` bypassed `ErrorBoundary` and SSR visibility:
  > "In 1.x, `resource.error` provided an alternative branching path that bypassed `ErrorBoundary` entirely. Code could check `.error` inline and render error UI without ever throwing — which meant `ErrorBoundary` wouldn't catch it, SSR couldn't know the tree had failed, and error handling was split between two mechanisms that didn't compose"
  [RFC: Async data (05-async-data.md)](file:///C:/Users/thinl/dev/solid/documentation/solid-2.0/05-async-data.md#L405), `solid-js@2.0.3 (commit fcaa0510)`, accessed 2026-11-23, Direct.
- **Problems with `resource.mutate` (non-granular, identity-losing, racy):**
  > "In 1.x, `mutate` replaced the resource value wholesale. This had several problems: no granular updates (the entire list re-rendered), no reconciliation (identity lost on every mutation), and no protection against race conditions (concurrent mutations could clobber each other)"
  [RFC: Async data (05-async-data.md)](file:///C:/Users/thinl/dev/solid/documentation/solid-2.0/05-async-data.md#L376), `solid-js@2.0.3 (commit fcaa0510)`, accessed 2026-11-23, Direct.
- **Stale-vs-fallback UX (`Loading` + `on` + `isPending` vs 1.x `.loading`):** Solid 2.0 distinguishes initial branch readiness (`<Loading>`) from in-flight input changes (`isPending(() => expr)`) so revalidation does not kick rendered UI back to fallback unless opted in via `<Loading on={...}>`; moreover, 1.x `.loading` fired on plain `refetch()`, whereas 2.0 treats bare `refresh()` as a quiet re-ask unless `affects()` is declared. [RFC: Async data (05-async-data.md)](file:///C:/Users/thinl/dev/solid/documentation/solid-2.0/05-async-data.md#L59-L131), `solid-js@2.0.3 (commit fcaa0510)`, accessed 2026-11-23, Direct.
- **Removal of `startTransition` / `useTransition` and `batch`:**
  > "Keeping explicit transition wrappers: rejected because transitions are a scheduling concern that should be inferred and managed by the runtime."
  [RFC: Async data (05-async-data.md)](file:///C:/Users/thinl/dev/solid/documentation/solid-2.0/05-async-data.md#L445), `solid-js@2.0.3 (commit fcaa0510)`, accessed 2026-11-23, Direct; see also [MIGRATION.md](file:///C:/Users/thinl/dev/solid/documentation/solid-2.0/MIGRATION.md#L784), `solid-js@2.0.3 (commit fcaa0510)`, accessed 2026-11-23, Direct (all writes batched by default on microtasks, removing explicit `batch`).
- **Tearing prevention via transaction holds and `latest()` rules:** Solid 2.0 documents that async holds prevent partial frames from tearing:
  > "async holds when a render effect reads it and no `Loading` boundary catches it. So a `latest()` view is never shown beside a half-computed derivation of itself... The fallback **follows the frame**: it lands with the same frame as the change that caused it."
  [RFC: Async data (05-async-data.md)](file:///C:/Users/thinl/dev/solid/documentation/solid-2.0/05-async-data.md#L92-L170), `solid-js@2.0.3 (commit fcaa0510)`, accessed 2026-11-23, Direct.
- **Write-back computations (`createComputed`) and accidental leaks (`createRoot`):** Solid 2.0 replaced `createComputed` because write-back computations were harder to reason about in an async/split-effects model, and made nested `createRoot` parent-owned by default to prevent accidental unowned memory leaks. [RFC: Signals, derived primitives, ownership, and context (02-signals-derived-ownership.md)](file:///C:/Users/thinl/dev/solid/documentation/solid-2.0/02-signals-derived-ownership.md#L13-L206), `solid-js@2.0.3 (commit fcaa0510)`, accessed 2026-11-23, Direct.

## Key Question 2: How Rust reactive and GPU UI frameworks model async derived state, loading/suspense boundaries, and fine-grained reactivity

### Takeaway

Web-oriented Rust UI frameworks (`reactive_graph`/Leptos and Dioxus) provide explicit async reactive nodes (`AsyncDerived` / `Resource<T>`) and `<Suspense>`/`SuspenseBoundary` integration, whereas native GPU UI frameworks (Floem, GPUI, Xilem) keep their UI/reactive layers synchronous and bridge async futures via signal writes, foreground/background executor tasks, or typed message channels.

## Key Question 3: JS runtime semantics in Solid 2.0's async signal model vs. Rust equivalents and divergences

### Takeaway

Solid 2.0 relies heavily on JS exceptions (`NotReadyError` and `ContextNotFoundError`) across arbitrary synchronous call stacks, GC/unobserved disposal, global microtask flushing, JS `Proxy` stores/props, and monkey-patching global `Promise`/`fetch` during hydration—whereas Rust UI frameworks replace exceptions with `Result`/`Option`/`.suspend()?`, GC with arena/slotmap owners (`ArenaItem`, `Scope`) or RAII (`Task`), and `Proxy` with typed reactive fields/lenses or explicit `Entity` updates.

### Cited findings

- **Throwing `NotReadyError` across arbitrary call stacks:**
  - Solid 2.0 documents `throw new NotReadyError();` as the mechanism to signal "not ready" through the reactive graph, caught by `<Loading>` boundaries and the front half of render effects without changing return types to `T | undefined`. [CHEATSHEET.md](file:///C:/Users/thinl/dev/solid/packages/solid/CHEATSHEET.md#L676-L677), [MIGRATION.md](file:///C:/Users/thinl/dev/solid/documentation/solid-2.0/MIGRATION.md#L527), [RFC: Async data (05-async-data.md)](file:///C:/Users/thinl/dev/solid/documentation/solid-2.0/05-async-data.md#L14-L36), `solid-js@2.0.3 (commit fcaa0510)`, accessed 2026-11-23, Direct; see also [morello.dev via search summary](https://vertexaisearch.cloud.google.com/grounding-api-redirect/AUZIYQGMvEaWfBuhFNkYvo-j1xvElzTCpeeRMPd1rMgnNRPojKIasC-97_E_7WC8hyDMSRCBwPEOLXPGKokZ9g-A4oaOosJ8zYSkHwgnsTdGa9ZjxW63nWWdZCGSCq1-eH4A62uA-wg==), undated, accessed 2026-11-23, Supported.
  - Rust has no general exception unwinding for control flow; Dioxus models boundary suspension via explicit `Result`-returning `.suspend()?` propagation in component functions. [dioxuslabs.com via search summary](https://vertexaisearch.cloud.google.com/grounding-api-redirect/AUZIYQFHlTJIuZNiKaW1YeyuMsUHSMC5SA6VkFuHbpOdm607L2VkDyidh5B1_X5RyWKu7jMXincBlmNklAUMojqNskbJ149QkTE5FIQEbx_jeGnHPR8i3-KxNDFU_NyDZEA7qijIrgwHzlKmoCktaapvH8oHhkQ=), undated, accessed 2026-11-23, Direct (via docs summary).
- **GC'd nodes & `unobserved` vs. Rust arena/owner handles and RAII:**
  - Solid 2.0 uses `createMemo(..., { lazy: true })` for autodisposal when subscriber count drops to zero and `{ unobserved }` callbacks when a signal/memo loses all subscribers, alongside owner-tree disposal (`createRoot`). ### Inferences

- **Non-throwing Rust async propagation:** Because Rust lacks non-local exceptions across arbitrary closures (`Fn() -> T`), adopting Solid 2.0's `NotReadyError` literally in Rust would require either explicit `Result<T, Pending>` / `.suspend()?` propagation (like Dioxus) or a separate per-node readiness bit checked by boundary/effect schedulers (closer to Leptos `AsyncDerived`/`Suspense`), rather than transparent `T`-returning accessors that unwind on read. (Inferred from Solid 2.0 `CHEATSHEET.md#L676-L677`, Dioxus `.suspend()?`, and Leptos `AsyncDerived`.)
- **Split compute/apply fits GPU UIs:** Solid 2.0's two-phase `createEffect(compute, apply)` maps cleanly to Rust retained/GPU UI architectures where reactive graph evaluation (compute) is separated from tree mutation, layout, and GPU command submission (apply), avoiding borrow-checker conflicts between graph reads and widget tree writes. (Inferred from `MIGRATION.md#L119-L137` and Xilem/Masonry retained widget separation.)
- **Generator `action` vs Rust `Future`:** Solid 2.0's `action(function* () { ... yield ... })` relies on JS generators driving an explicit transaction state machine, which in Rust corresponds closely to custom `Future` polling or async state machines scoped to an `action` handle—except Rust's `Drop` gives deterministic cancellation on supersede without manual `AbortController` registration. (Inferred from `05-async-data.md#L43-L51` and GPUI `Task` / Xilem `task` drop cancellation.)

## 1. How do `computed`, `signal`, `createSignal(fn)`, and `createMemo` detect and handle `Promise` and `AsyncIterable` return values (specifically `handleAsync` in `core/async.ts` and `core/core.ts`), and what happens on re-evaluation / cancellation when an upstream dependency changes while an async task is in flight?

### Takeaway

`signal()` stores plain values synchronously with no async machinery, while `computed()` (underlying both `createMemo` and `createSignal(fn)`) runs its compute function inside `recompute()`, passes any non-null object return value (unless `CONFIG_SYNC` in prod or self-registered) to `handleAsync()`, and inspects `Symbol.asyncIterator` and `isThenable()` untracked. Re-evaluation supersedes any prior flight by clearing `_inFlight` and invoking `_flightTeardown` (which calls `it.return?.()` and `onSupersede` hooks), causing stale promise/iterator callbacks to ignore their own results.

## 3. How do derived writable signals (`createSignal(fn)`), `resolve()`, and `from()` integrate async sources into the same signal graph, and how does Solid 2.0 prevent glitch/zombie reads when async values settle?

### Takeaway

`createSignal(fn)` creates a non-autodisposing `computed` whose setter (`setMemo`) writes through `setSignal` (marking `REACTIVE_MANUAL_WRITE` or dirtying a held derivation so the hold re-derives over the write); `resolve(fn)` creates an internal `computed` marked `CONFIG_REDERIVE` inside `createRoot` that retries on `NotReadyError` and delivers the first settled value/error via `queueMicrotask`; and `from(source)` adapts push/Observable/`AsyncIterable` sources into a Solid-owned `AsyncIterable` tied to `onSupersede` and `cleanup`. Glitch and zombie reads are prevented via topological height ordering (`_height`), staged writes (`_pendingValue` vs `_value`) with frame/unflushed-write guards (`unflushedValue`, `frameRead`, `stagedScreen`), and `REACTIVE_ZOMBIE` / `REACTIVE_DISPOSED` / `_inFlight` identity guards.

# Solid.js 2.0 비동기 시그널 아키텍처와 Rust GPU UI 설계 적용 분석

## 질문

Solid.js 2.0(`solid-js@2.0.3` / `@solidjs/signals@2.0.3`, 로컬 체크아웃 `C:\Users\thinl\dev\solid`, 커밋 `fcaa0510`)은 프론트엔드 비동기 코드를 인체공학적으로 다루기 위해 비동기 시그널을 어떻게 통합하는지, 그리고 이를 본뜬 Rust GPU 가속 UI 라이브러리를 설계할 때 어떤 핵심 메커니즘, 형식 불변식, 설계 트레이드오프가 적용되는가?

기준일: `2026-11-23`

## 핵심 답변

Solid 2.0은 1.x의 `createResource`와 `startTransition`을 폐지하고 일반 `computed()`(즉 `createMemo`와 함수형 `createSignal`)가 `Promise`와 `AsyncIterable`을 직접 반환하다가 아직 준비되지 않았으면 `NotReadyError`를 동기적으로 던지도록 비동기 시그널을 단일 그래프로 통합했습니다. 소비자는 `async`/`await`나 `T | undefined` 분기 없이 동기 접근자처럼 값을 읽습니다. 런타임은 `pre-L2` 모델을 대체한 **L2 보류(hold) 모델** 위에서 토폴로지 높이 정렬, `_value`(화면 커밋 값)와 `_pendingValue`(스테이징 값) 이중 슬롯, `Transaction`과 서브프레임 `Lane`을 조합해 부분 렌더링(tearing)과 좀비 읽기를 막고 `<Loading>`, `<Errored>`, `<Reveal>`, 자동 낙관적 롤백(`action` + `createOptimistic`)을 조율합니다.

반면 기존 Rust UI 생태계에서 웹 프레임워크(Leptos `reactive_graph`, Dioxus)는 명시적 비동기 노드나 `.suspend()?` 전파를 채택하고 GPU 네이티브 프레임워크(Floem, GPUI, Xilem)는 동기 UI 계층과 비동기 실행기를 분리해 시그널, 엔티티, 메시지 채널로 결과를 돌려줍니다. Solid 2.0을 본뜬 Rust GPU UI를 설계할 때는 JS 예외 기반 제어 흐름(`NotReadyError`), GC 자동 폐기, 전역 `Promise`/`fetch` 가로채기, `Proxy` 기반 추적 프롭스를 그대로 복제하려 하기보다, push-pull 의존 그래프, 스테이징과 커밋의 이중 버퍼링, 순수 계산과 부작용 적용을 나눈 `createEffect(compute, apply)`, 명시적 아레나·RAII 소유자 모델, 상태 머신 기반 경계와 레인을 결합하는 방향이 적합합니다.

## 조사 결과

### 1. Solid 2.0이 비동기 시그널을 통합하고 1.x의 `createResource`·`startTransition`을 제거한 배경

Solid 2.0의 공식 RFC와 마이그레이션 문서는 1.x의 `createResource`와 명시적 `startTransition`, `batch`가 비동기와 동기를 이원화된 프리미티브와 수동 스케줄링 래퍼로 갈라놓았던 한계를 기록합니다. 구체적으로 `05-async-data.md` RFC는 세 가지 동기를 명시합니다 ([05-async-data.md](file:///C:/Users/thinl/dev/solid/documentation/solid-2.0/05-async-data.md#L13-L15), `solid-js@2.0.3 (commit fcaa0510)` / RFC 동결 `2.0.0 (2026-11-17)` `[Direct]`).

1. **단일 모델(One model):** 비동기를 별도 리소스 프리미티브가 아니라 계산 노드 자체의 속성으로 편입해 이펙트, 경계, SSR·하이드레이션이 비동기를 일관되게 다루도록 했습니다.
2. **타입 개선(Better types):** 비동기 값마다 `T | undefined` 같은 로딩 구멍을 타입에 남기는 대신 준비되지 않은 상태를 `<Loading>` 경계로 표현하게 했습니다.
3. **합성성(Composability):** 계산 노드가 비동기를 품으면서 별도 리소스 조합기 없이 동기와 비동기 파생 값을 자연스럽게 섞을 수 있게 했습니다.

이 설계는 소비자에게 `async`/`sync` 함수 색상이 전염되지 않는 "무색(colorless)" 비동기 반응성을 지향한다는 2차 검색 요약 설명과도 맞닿아 있습니다 ([dev.to 검색 요약 출처](https://vertexaisearch.cloud.google.com/grounding-api-redirect/AUZIYQGLJPdjEg8cDGbRLNMrpbfNlupEKo_cw1I2tn9V30CR6bIVt-f9ua7d05f9SEKWrgIU99Ary8kbyIIoQiP-8HqMqpZNhQ_TJCgojmkI1DbZTQxyHsxIfXW8-8VGr82Z2woUN6GKNUAkc0vcI6Yv7NeBj0qvGVbwvuH-QQ==), 날짜 미상, 검색 요약 출처 `[Supported]`).

1.x에서 발생하던 구체적인 결함들도 제거 사유로 기록되어 있습니다. `resource.error`는 `ErrorBoundary`를 거치지 않고 인라인 분기로 에러를 처리할 수 있어서 SSR이 실패를 알지 못하고 에러 경로가 둘로 쪼개지는 문제를 낳았습니다 ([05-async-data.md](file:///C:/Users/thinl/dev/solid/documentation/solid-2.0/05-async-data.md#L405), `solid-js@2.0.3 (commit fcaa0510)` `[Direct]`). `resource.mutate`는 리스트 전체를 통째로 덮어써 세분화 갱신과 정체성 보전이 안 되었고 동시 변이가 서로를 덮어쓰는 경합에도 취약했습니다 ([05-async-data.md](file:///C:/Users/thinl/dev/solid/documentation/solid-2.0/05-async-data.md#L376), `solid-js@2.0.3 (commit fcaa0510)` `[Direct]`). 또한 1.x `.loading`은 단순 `refetch()`에도 동작했지만 2.0은 최초 브랜치 준비 여부(`<Loading>`)와 이미 뜬 화면의 입력 변경 진행 여부(`isPending`)를 나눕니다. 기본 `refresh()`는 조용한 재요청으로 두어 명시적 표시가 필요할 때만 `affects()`나 `<Loading on={...}>`을 쓰도록 바꿨습니다 ([05-async-data.md](file:///C:/Users/thinl/dev/solid/documentation/solid-2.0/05-async-data.md#L59-L131), `solid-js@2.0.3 (commit fcaa0510)` `[Direct]`).

스케줄링 측면에서 2.0은 `startTransition`, `useTransition`, `batch`를 모두 제거했습니다. 트랜지션은 개발자가 수동으로 감싸야 할 대상이 아니라 런타임이 추론·관리하는 스케줄링 관심사라는 판단 때문이며 ([05-async-data.md](file:///C:/Users/thinl/dev/solid/documentation/solid-2.0/05-async-data.md#L445), `solid-js@2.0.3 (commit fcaa0510)` `[Direct]`), 모든 쓰기는 기본적으로 마이크로태스크에 자동 배치되고 즉시 배출이 필요할 때만 `flush()`를 씁니다 ([MIGRATION.md](file:///C:/Users/thinl/dev/solid/documentation/solid-2.0/MIGRATION.md#L784), `solid-js@2.0.3 (commit fcaa0510)` `[Direct]`). 비동기·분할 이펙트 모델에서 추론하기 어려웠던 쓰기-되돌림 계산인 `createComputed`를 없애고 의도치 않은 비소유 메모리 누수를 줄이기 위해 중첩 `createRoot`를 기본 부모 소유로 바꾼 것도 같은 맥락의 정리입니다 ([02-signals-derived-ownership.md](file:///C:/Users/thinl/dev/solid/documentation/solid-2.0/02-signals-derived-ownership.md#L13-L206), `solid-js@2.0.3 (commit fcaa0510)` `[Direct]`).

### 2. 코어 Push-Pull 그래프와 `NotReadyError` 기반 무색 비동기 전파

#### `signal`과 `computed`의 분리 및 `Promise`·`AsyncIterable` 감지

단순 `signal(v, options)`은 동기 값만 담는 `RawSignal`을 할당합니다. 스토어가 접근된 말단(touched leaf)마다 시그널을 하나씩 만들기 때문에 메모리를 아끼려고 `_fn`과 `_statusFlags`를 두지 않고 `_value`, `_pendingValue`, `_subs`, `_subsTail`, `_equals`, `_config`, `_time`, `_notifiedAt`, `_x: null`만 할당합니다(코드 주석에는 `No _time/_fn/_statusFlags`라고 적혀 있으나 실제 객체 리터럴 1365행에는 `_time: clock`이 포함되어 있음 — 검증 단계에서 수정) ([core.ts](file:///C:/Users/thinl/dev/solid/packages/signals/src/core/core.ts#L1338-L1376), `@solidjs/signals@2.0.3 (commit fcaa0510)` `[Direct]`). 반면 `createMemo`와 함수형 `createSignal(fn)`은 모두 내부 `computed()` 노드를 감쌉니다. `createMemo`는 `read.bind(null, node)` 접근자만 반환하고 `createSignal(fn)`은 `CONFIG_AUTO_DISPOSE` 비트를 끈 뒤 `[accessor(node), setMemo.bind(null, node)]` 쌍을 반환해 수동 덮어쓰기(`setMemo`)와 의존성 재계산을 한 노드에 통합합니다 ([signals.ts](file:///C:/Users/thinl/dev/solid/packages/signals/src/signals.ts#L143-L147), [signals.ts](file:///C:/Users/thinl/dev/solid/packages/signals/src/signals.ts#L416-L427), [signals.ts](file:///C:/Users/thinl/dev/solid/packages/signals/src/signals.ts#L520-L525), `@solidjs/signals@2.0.3 (commit fcaa0510)` `[Direct]`).

`recompute(el, create)`가 `el._fn(value)`를 실행하면 반환값이 `null`이 아닌 객체인지 확인하고(프로덕션 모드의 `CONFIG_SYNC`나 자가 등록 예외 제외) 비동기 후보를 `handleAsync(el, fnResult)`로 넘깁니다 ([core.ts](file:///C:/Users/thinl/dev/solid/packages/signals/src/core/core.ts#L560-L582), `@solidjs/signals@2.0.3 (commit fcaa0510)` `[Direct]`). `handleAsync()`는 `untrack()` 안에서 `Symbol.asyncIterator`와 `isThenable()`을 순서대로 검사합니다. 개발 모드(`__DEV__`)에서 `CONFIG_SYNC` 노드가 `thenable`이나 이터레이터를 돌려주면 `SYNC_NODE_RECEIVED_ASYNC` 오류를 던집니다. 일반 동기 객체라면 `_inFlight = null`, `CONFIG_ASYNC` 해제, `_loading = false` 정리 후 그대로 반환합니다 ([async.ts](file:///C:/Users/thinl/dev/solid/packages/signals/src/core/async.ts#L313-L319), [async.ts](file:///C:/Users/thinl/dev/solid/packages/signals/src/core/async.ts#L389-L432), `@solidjs/signals@2.0.3 (commit fcaa0510)` `[Direct]`).

유효한 비동기 객체가 감지되면 `handleAsync()`는 `ext(el)._inFlight = result`, `CONFIG_ASYNC`, `_q`를 기록하고 `_pendingSources`를 비워 이전 질문의 보류 출처가 새 응답을 붙잡지 못하게 합니다 ([async.ts](file:///C:/Users/thinl/dev/solid/packages/signals/src/core/async.ts#L436-L443), `@solidjs/signals@2.0.3 (commit fcaa0510)` `[Direct]`). 이후 분기는 객체 종류에 따라 갈립니다.

- **`Promise` / Thenable:** `.then()`이 등록 시점에 즉시 동기 실행되면 그 값을 취하거나(해결 값이 `AsyncIterable`이면 `flattenIfIterable`로 평탄화), 동기 거부는 에러로 다시 던집니다. 미완료 상태라면 `loadingValue` 옵션으로 `_loading`이 켜졌을 때만 직전 `el._value`를 돌려주고 그렇지 않으면 `throw new NotReadyError(context!)`를 던집니다. 훗날 비동기로 해결될 때 `el._x?._inFlight === result && !(el._flags & REACTIVE_DISPOSED)` 조건을 만족하면 `asyncWrite(v)`로 값을 쓰고 `settleAutodispose()`를 호출합니다 ([async.ts](file:///C:/Users/thinl/dev/solid/packages/signals/src/core/async.ts#L640-L718), `@solidjs/signals@2.0.3 (commit fcaa0510)` `[Direct]`).
- **`AsyncIterable`:** `consumeIterator()`가 `source[Symbol.asyncIterator]()`를 얻어 소유자 `cleanup`과 `ext(el)._flightTeardown`에 `it.return?.()` 닫기 함수를 등록합니다. 초기 동기 루프에서 즉시 반환되는 `IteratorResult`들을 소진한 뒤, 이후 비동기 스텝에서는 `asyncWrite(r.value, iterateOrRelease)`가 값을 쓴 뒤에 `settleAutodispose()`를 확인하고 다음 `next()`를 당겨 오므로 구독자가 사라진 스트림이 영원히 펌핑되는 일을 막습니다 ([async.ts](file:///C:/Users/thinl/dev/solid/packages/signals/src/core/async.ts#L539-L633), `@solidjs/signals@2.0.3 (commit fcaa0510)` `[Direct]`).
- **상위 변경과 선점(supersession):** 상위 의존성이 바뀌어 `recompute(el, false)`가 다시 돌면 먼저 `_inFlight = null`로 지우고 `releaseFlightTeardown(el)`을 호출합니다. 이 호출은 등록된 이터레이터의 `it.return?.()`과 동기 패스 중 `onSupersede(fn)`로 연결해 둔 취소 콜백을 커밋이나 폐기 시점까지 미루지 않고 즉시 실행합니다. 뒤늦게 도착한 이전 비행의 콜백은 `el._x?._inFlight !== result` 확인에 걸려 아무 일도 하지 않습니다. 대체 패스가 동기로 정착하면 `settlePendingSource(el)`이 호출돼 예전 비행에 묶여 있던 하위 노드를 깨웁니다 ([core.ts](file:///C:/Users/thinl/dev/solid/packages/signals/src/core/core.ts#L434-L438), [core.ts](file:///C:/Users/thinl/dev/solid/packages/signals/src/core/core.ts#L822-L826), [async.ts](file:///C:/Users/thinl/dev/solid/packages/signals/src/core/async.ts#L321-L351), [async.ts](file:///C:/Users/thinl/dev/solid/packages/signals/src/core/async.ts#L450), [async.ts](file:///C:/Users/thinl/dev/solid/packages/signals/src/core/async.ts#L488), `@solidjs/signals@2.0.3 (commit fcaa0510)` `[Direct]`).

#### `NotReadyError` 동기 전파와 `resolve`·`from` 통합

`NotReadyError`는 `Error`를 상속하며 `source` 필드를 가집니다. 대기 중인 소스를 읽을 때마다 제어 흐름용으로 던져지므로 프로덕션에서는 `Error.stackTraceLimit`을 0으로 내려 스택 수집 비용을 없앱니다. 사용자 예외는 `cause`와 `source`를 담은 `StatusError`로 감싸고 `unwrapStatusError()`로 원본을 꺼냅니다 ([error.ts](file:///C:/Users/thinl/dev/solid/packages/signals/src/core/error.ts#L25-L68), `@solidjs/signals@2.0.3 (commit fcaa0510)` `[Direct]`).

## 합리적 추론

1. **Promise의 논리적 선점 대 `AsyncIterable`·RAII의 물리적 취소 (`[Inferred]`):** `core/async.ts#L321-L327`, `#L450`, `#L488`, `#L554-L556`에서 `AsyncIterable`과 `onSupersede` 훅은 `releaseFlightTeardown()`으로 즉시 정리되지만 `Promise` 자체를 취소하는 경로는 보이지 않으므로, Solid 2.0에서 진행 중 `Promise`의 선점은 물리적 중단이 아니라 `_inFlight !== result` 비교로 stale 착지를 무시하는 논리적 폐기에 의존하는 것으로 보입니다. 따라서 Rust 이식 시 `Task` 드롭을 쓰면 불필요한 백그라운드 계산까지 즉시 중단할 수 있을 것으로 추정됩니다.
2. **`createSignal(fn)`의 통합 구조 (`[Inferred]`):** `signals.ts#L420-L426`이 `computed`에서 `CONFIG_AUTO_DISPOSE`만 제거하고 `setMemo`를 연결하며 `core.ts#L2389-L2419`가 `REACTIVE_MANUAL_WRITE`와 보류 재파생을 처리하는 점으로 미루어, 단일 프리미티브가 비동기 파생과 수동 가변 상태 역할을 겸하도록 설계된 것으로 판단됩니다.
3. **`onSettled`의 보류 지연 동작 (`[Inferred]`):** `signals.ts#L1234-L1264`에서 소유 스코프 `onSettled`는 `trackedEffect`에 위임하고 비소유 스코프는 `dirtyQueue`가 빌 때까지 `EFFECT_USER`에 재등록하며 `scheduler.ts#L1264-L1273`에서 열린 트랜지션이 이펙트 큐를 `t._queues`에 보류한다는 점을 함께 보면, 두 형태 모두 보류 중인 트랜지션이 커밋되기 전에는 실행되지 않도록 동작하는 것으로 해석됩니다.
4. **Rust에서의 비예외 `NotReady` 전파 방식 (`[Inferred]`):** Rust에는 임의 `Fn() -> T` 클로저 경계를 넘는 예외 언와인딩이 없으므로, Solid 2.0 `CHEATSHEET.md#L676-L677`의 `throw new NotReadyError()`를 그대로 옮기기보다 Dioxus식 `Result<T, Pending>` + `.suspend()?` 명시 전파나, Leptos `AsyncDerived`와 유사하게 노드별 준비 비트를 계산 그래프와 경계 스케줄러가 전파하는 모델 중 하나를 택할 가능성이 높습니다.
5. **분할 `createEffect(compute, apply)`의 빌림 검사기 적합성 (`[Inferred]`):** `MIGRATION.md#L119-L137`의 순수 계산·부작용 분리와 Xilem/Masonry의 선언적-보유 위젯 분리를 나란히 놓으면, Rust GPU UI에서 반응형 그래프 읽기(`&Graph`)와 보유 위젯 트리, 레이아웃, GPU 명령 기록(`&mut Tree`)을 다른 단계로 떼어 놓아 빌림 충돌을 피하는 데 유리할 것으로 보입니다.
6. **`action` 상태 머신과 Rust `Future` (`[Inferred]`):** `05-async-data.md#L43-L51`의 제너레이터 기반 `action` 상태 머신과 GPUI `Task`·Xilem `task`의 드롭 취소 패턴을 비교하면, Rust에서는 `action` 핸들에 수명이 묶인 커스텀 `Future` 상태 머신으로 다단계 트랜지션을 표현하고 `Drop`으로 수동 `AbortController` 등록 부담을 줄일 수 있을 것으로 추정됩니다.

## 상충 및 긴장 지점

1. **`@solidjs/universal`의 `render()` 대 `scheduler.ts`가 기술한 `render()`의 `enforceLoadingBoundary` 계약**
   - **쪽 A (`universal.ts`):** `packages/universal/src/universal.ts#L581-L618`(`@solidjs/universal@2.0.3 (commit fcaa0510)` `[Direct]`)의 `render()`는 `enforceLoadingBoundary`를 호출하지 않으면서도 주석으로 "경계 밖 최상위 비동기가 활성 트랜지션에서 초기 커밋을 보류했다가 정착 시 원자적으로 부착하며 `@solidjs/web`의 `render`와 같다"고 설명합니다.
   - **쪽 B (`scheduler.ts`):** `packages/signals/src/core/scheduler.ts#L791-L819`(`@solidjs/signals@2.0.3 (commit fcaa0510)` `[Direct]`)의 `enforceLoadingBoundary` JSDoc은 "`render()`만이 초기 마운트를 감싸 최상위 미포착 비동기 읽기가 진단(`_hitUnhandledAsync`)을 표출하게 한다"고 적고 있습니다.
   - **판단:** 두 경로 모두 런타임 동작 자체는 `GlobalQueue.notify`의 `joinFuture(null)`로 초기 마운트를 보류한다는 점에서 같지만 개발 모드 경고 발생 계약에서는 어긋납니다. `@solidjs/web`의 `render()` 소스를 직접 읽지 않았으므로 `@solidjs/web` 쪽의 실제 호출 여부는 단정할 수 없으나, 현재 읽은 `@solidjs/universal` 코드에는 `enforceLoadingBoundary` 호출이 없으므로 커스텀 렌더러를 만들 때 최상위 미포착 비동기를 조용히 보류할지 경고할지 명시적으로 결정해야 합니다.

2. **`L1`/`L2`/`L3` 계층 가정 대 문서의 `pre-L2`/`L2` 및 3계층 규범 체계**
   - **쪽 A (3단계 구현 계층 가정):** 질문이나 일부 설계 해석에서는 Solid 2.0 아키텍처에 `L1`, `L2`, `L3`의 세 구현 계층이 존재하는 것으로 전제합니다.
   - **쪽 B (실제 2.0.3 코드와 문서):** `INTERNALS-ASYNC-STATE.md` §0, `SPEC-ASYNC-SEMANTICS.md`, `RULES-FUNDAMENTALS.md`(`@solidjs/signals@2.0.3 (commit fcaa0510)` `[Direct]`)에서 확인되는 아키텍처 구분은 `pre-L2`(이전 설계)와 `L2`(보류 모델, `2026-10-04`)뿐입니다. `L1`이나 `L3`의 정의는 탐색한 문서에 존재하지 않습니다. 대신 규범 체계가 `Fundamentals` > `Derived rules` > `Scenarios`의 3계층으로 나뉘어 있습니다.
   - **판단:** 현재 근거는 `pre-L2` 대 `L2` 모델과 3계층 규범 체계만을 직접 뒷받침하며 `L1`/`L3` 구현 계층의 존재는 확인되지 않았습니다.

3. **설계 요약 문서의 `REACTIVE_STAGED_READ` 대 코드의 `REACTIVE_FRAME_READ`**
   - **쪽 A (`INTERNALS-ASYNC-STATE.md` §0):** `INTERNALS-ASYNC-STATE.md#L22`(`2026-10-04` `[Direct]`)는 플러시 보류 시 커밋된 값으로 재파생하는 비트플래그를 `REACTIVE_STAGED_READ`로 기재합니다.
   - **쪽 B (코어 구현):** 커밋 `fcaa0510`의 `core/constants.ts#L22-L28`, `core/core.ts#L1771-L1773`, `core/scheduler.ts#L1353-L1413`(`@solidjs/signals@2.0.3` `[Direct]`)에는 이 비트플래그가 `REACTIVE_FRAME_READ`(레인 읽기에서는 `REACTIVE_FRAME_READ | REACTIVE_SCREEN_READ`)로 구현되어 있습니다.
